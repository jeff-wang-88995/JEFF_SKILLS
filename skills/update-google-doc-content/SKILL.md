# 更新 Google 文件內容

## 目標

以完整 Markdown 原稿為唯一文字基準，核對新的事實來源後只修改必要內容。保存可持續維護的原稿，並在最終回覆中完整渲染，讓使用者能直接複製到 Google 文件。

## 工作流程

### 1. 確認完整原稿

依下列順序尋找原稿：

1. 使用者明確指定的本地 Markdown 檔案。
2. 使用者在目前對話中貼出的完整原文。
3. 使用者確認為完整版本的其他純文字來源。

只有截圖、節錄、摘要或零散段落時，不得推測或重建全文。先明確說明缺少完整原文，並請使用者提供原稿或指定檔案。

不要把程式碼、既有產品介面或先前模型回答視為原文替代品。它們只能作為事實核對來源。

### 2. 建立更新依據

- 先閱讀完整原稿，保留原有標題層級、章節順序、措辭、表格及範例。
- 若內容描述程式行為，唯讀檢查實作、版本、UI 名稱、設定與實際流程。
- 若使用者提供新版需求或差異清單，以該內容作為更新依據。
- 分開記錄「確認需要修改」與「尚無證據需要修改」的內容。
- 無法確認的新資訊不得寫成既定事實；保留原文並標示待確認，或向使用者說明缺口。

### 3. 採最小變更

- 只修改過時、錯誤、矛盾或因新功能而必須補充的內容。
- 未受影響的句子、標題、段落、順序、表格與範例保持不動。
- 新功能優先插入最接近的既有章節，不任意重整全文。
- 只有原結構會導致邏輯錯誤、重複或無法理解時，才局部重寫。
- 不做純風格潤飾、同義改寫或未被要求的內容擴寫。
- 更新完成後比對原稿，確認所有差異都有明確理由。

### 4. 保存 Markdown 原稿

使用者指定本地原稿且要求更新時：

1. 編輯同一份 Markdown，除非使用者指定新路徑。
2. 保持 UTF-8 no BOM 與 LF。
3. 保存後重新讀取或檢查差異，確認內容完整且無亂碼。

若使用者沒有指定保存位置，不自行在專案建立文件；僅在回覆中交付完整富格式內容。若是否寫入檔案會改變使用者資料，先確認其意圖。

### 5. 輸出可貼入 Google 文件的格式

最終回覆必須：

- 貼出更新後的完整全文，不只提供差異摘要或檔案連結。
- 使用 Markdown 標題、粗體、編號、項目符號與表格，讓聊天介面先渲染成富格式。
- 不得用單一外層程式碼區塊包住全文。
- 文件中真正的程式碼、公式、路徑或純文字範例，可保留各自的程式碼區塊。
- 不在文件正文中混入修改紀錄、作業說明或模型備註。
- 在全文前用一句話說明可直接從畫面複製並貼入 Google 文件。

若全文過長而系統無法在單次回覆中完整提供，先告知限制並分段交付；不得無提示地截斷。

### 6. 回報修改內容

在不干擾可複製正文的位置，簡短說明：

- 使用的完整原稿來源。
- 實際更新的章節或事實。
- 是否保存本地 Markdown。
- 哪些主要章節刻意保持不變。

使用者只要求貼出正文時，省略額外回報，直接交付完整富格式內容。

## 其他輸出格式

- 預設不建立 DOCX、PDF，也不直接操作 Google Docs。
- 使用者明確要求 DOCX 時，改用可用的文件製作 Skill，並依其渲染與驗證流程執行。
- 使用者明確要求直接更新 Google 文件時，使用可用的 Google Docs／Drive 連接器；沒有連接器時說明限制，不假裝已更新。
- Markdown 原稿仍作為後續更新的首選基準，除非使用者另有指定。

## 完成檢查

- 已取得並完整閱讀原稿。
- 所有內容變更都有事實或需求依據。
- 未受影響的內容沒有被重新措辭。
- 版本、UI 名稱、路徑與範例互相一致。
- 本地原稿在需要時已保存並通過 UTF-8 no BOM、LF 與亂碼檢查。
- 回覆包含完整正文，且全文沒有被外層程式碼區塊包住。
- 標題、粗體、清單與表格可在聊天介面正常渲染。
