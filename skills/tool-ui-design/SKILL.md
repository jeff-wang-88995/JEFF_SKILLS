# 工具 UI 設計與檢查

## 目標

依工具的真實任務、資訊量、狀態與平台限制設計 UI。不要把某次成功的排版結果變成所有工具的固定規則。

## 開始前

1. 先辨識使用者要討論、規劃、檢查或實作。
2. 使用者要求「先討論」或只要求檢查時，不得修改檔案。
3. 有 repository、現有介面或截圖時，先唯讀檢查實作與畫面，再提出判斷；不要只依控制項名稱猜測行為。
4. 閱讀 [通用決策框架](references/decision-framework.md)，依其方式整理任務、資訊、狀態、風險與量化比較。
5. 任務屬於 NVIDIA Omniverse、Kit 或 Composer 時，再閱讀 [Omniverse Kit UI 規則](references/omniverse-kit-ui.md)。一般工具 UI 不套用該平台規則。

## 工作流程

### 建立任務模型

確認主要使用者與主要成果，並區分：

- 常用操作與次要操作
- 必須持續可見的狀態與按需查看的細節
- 可編輯輸入、唯讀資訊與系統自動產生的值
- 暫存、預覽、已儲存與可還原狀態
- 寫入、覆蓋、刪除或其他高風險操作

缺少會改變設計方向的產品意圖時才詢問使用者。可以從程式、截圖或平台規則確認的事實，先自行檢查。

### 選擇呈現方式

依資訊的重要性、數量、文字長度、更新頻率、比較需求及可用空間，選擇單列、多列、表格、分組、收合區、詳細視窗或 Tooltip。

- 不規定統計資訊必須占幾行，也不以固定項目數決定是否收合。
- 關鍵資訊與重大風險不得只藏在 Tooltip。
- 唯讀欄位是否保留，取決於使用者是否需要確認、複製或避免選錯範圍。
- 條件式欄位只在對目前 Mode、Scope 或工作狀態有意義時顯示，但隱藏後仍須讓使用者知道實際作用範圍。
- 主要操作依任務順序與使用頻率安排；進階與高風險操作不得搶走主要流程的視覺優先權。

### 保護狀態與資料

- 切換選取、Mode、Scope、頁面或分頁，不得意外清除未儲存工作，除非產品流程明確要求。
- 寫入、覆蓋與刪除操作應依風險顯示實際目標、影響範圍、可否還原及必要確認。
- 不因 UI 整理而改變既有資料語意、預設值或持久化行為，除非使用者明確要求。

### 提案與實作

- 討論或規劃：提供設計理由、取捨及必要的簡圖或方案比較，不修改檔案。
- 檢查：回報具體問題、影響與建議，不自行實作修正。
- 實作：只修改使用者授權的範圍，保留未要求改變的功能，並依風險選擇成本最低且足以證明結果的驗證方式。
- 有多個具實質差異的方案時，依通用決策框架提供各項分數與綜合評分；只有一個合理方案時，不為了湊格式製造無意義選項。

### 驗證策略

- 語法、型別、Build、runtime 與視覺控制是可選的證據來源，不是每次實作都要全部執行。
- 依 [通用決策框架](references/decision-framework.md) 的風險分級做最低充分驗證。低風險小改不因涉及 UI 就預設啟動或控制實際應用程式。
- 優先使用靜態檢查、既有測試、Build、log 或現有截圖；只有較低成本的方法不足以回答具體排版、互動或 runtime 風險時，才使用實際應用程式或視覺控制。
- 若使用者要求快速處理、限制驗證時間或不要 GUI／視覺控制，遵守該偏好，並在回報中明確列出未驗證項目。
- 使用視覺控制前，先以一句話說明它要驗證的具體風險；採風險分級時不需為一般低風險操作額外停下等待確認。

## 數據與效率說明

- 可以量測時，提供實際像素、操作步數、點擊次數、控制項數量或百分比差異，並說明量測條件。
- 無法量測時，明確標示「估算」及範圍，不得把推測寫成實測結果。
- 介面變矮不等於效率提升；必須一起考慮可讀性、可發現性、錯誤風險與任務完成時間。

## 完成檢查

- 設計符合使用者要求的討論、規劃、檢查或實作範圍。
- 呈現方式由實際資訊與任務決定，沒有套用固定行數或固定版型。
- 主要、次要、進階與危險操作的層級清楚。
- 隱藏與 Tooltip 沒有移除完成任務所需的關鍵資訊。
- 未儲存狀態不會因無關的 UI 操作意外消失。
- 實測與估算清楚區分，多方案評分有一致依據。
- 若已實作，已完成與變更風險相稱的最低充分驗證，並明確區分已驗證與未驗證項目。
